# Архитектура Notification Platform

**Микросервисная платформа реал-тайм уведомлений на Golang**

## 1. Обзор

Платформа предназначена для надёжной доставки уведомлений пользователям в реальном времени с поддержкой offline-сценариев. 

Состоит из двух основных сервисов:
- `notification-service` - приём и надёжная публикация уведомлений
- `ws-notifier` - реал-тайм доставка по WebSocket с горизонтальным масштабированием

Ключевые требования, которые решает архитектура:
- **Надёжность доставки** (at-least-once)
- **Горизонтальное масштабирование**
- **Поддержка offline-пользователей**
- **Низкая задержка** доставки
- **Отслеживание статусов** уведомлений

## 2. Компоненты

| Компонент                | Назначение                                         | Масштабирование              | Технологии                   |
|--------------------------|----------------------------------------------------|------------------------------|------------------------------|
| **notification-service** | REST API + Outbox Dispatcher                       | Горизонтальное (1 лидер)     | Gin, GORM, NATS JetStream    |
| **ws-notifier**          | WebSocket Manager + доставка + работа с Redis      | Горизонтальное (N инстансов) | Gorilla/ws, Redis, NATS JS   |
| **NATS JetStream**       | Надёжная асинхронная шина между сервисами          | -                            | JetStream                    |
| **PostgreSQL**           | Persistent storage уведомлений и outbox-событий    | -                            | GORM + Транзакции + Триггеры |
| **Redis**                | Offline-хранилище + cross-node broadcast + Pub/Sub | -                            | ZSet + Strings + TTL         |
| **Nginx**                | Reverse Proxy / Load Balancer для ws-notifier      | -                            | -                            |

## 3. Технологический стек

- **Go 1.25**
- **NATS JetStream** - основная шина событий
- **PostgreSQL** + GORM
- **Redis** - хранение писем для offline и межнодовое взаимодействие

## 4. Архитектурные паттерны

### 4.1 Outbox Pattern (в notification-service)

- При создании уведомления **атомарно** сохраняются две записи в одной транзакции:
  - `notifications`
  - `outbox_events`
- Фоновые воркеры забирают события через `ClaimPendingOutboxEvents()` с использованием `UPDATE ... SKIP LOCKED`.
- Это гарантирует **at-least-once** доставку даже при падении сервиса или перезапуске.

### 4.2 Горизонтальное масштабирование WebSocket

`ws-notifier` может запускаться в нескольких инстансах. Для координации используется Redis:

1. При получении сообщения из NATS:
   - Проверяем, есть ли активное соединение **на этом инстансе**.
   - Если есть -> отправляем по WS + `MarkAsDelivered`.
   - Если нет -> сохраняем в Redis + публикуем в **Redis Pub/Sub broadcast** канал.
2. Все остальные инстансы `ws-notifier` получают broadcast и пытаются доставить сообщение, если у них есть соединение пользователя. Если есть -> доставляем и удаляем запись из Redis. Если нет -> не делаем ничего.

### 4.3 Offline Delivery

- При отключении пользователя сообщения сохраняются в Redis (с TTL в зависимости от приоритета).
- При новом WebSocket-подключении клиент сразу получает все накопленные сообщения (`GetUnread`).
- После успешной доставки сообщения удаляются из Redis.

## 6. Масштабирование и отказоустойчивость

- **notification-service**: можно запускать несколько реплик. Только одна выполняет роль Outbox Dispatcher (через env-флаг). В будущем планируется распределение лидерства ноды (для отказоустойчивости).
- **ws-notifier**: полностью горизонтально масштабируется. Количество инстансов ограничивается только ресурсами Redis и NATS.
- **NATS JetStream**: обеспечивает доставку сообщений.
- **PostgreSQL**: одна нода (в docker-compose). В проде рекомендуется работать с репликами.
- **Graceful shutdown** реализован во всех сервисах.
